## 2. 잘된 점

- **결정을 먼저 받고 시작했다.** 하드웨어, 펌웨어 프레임워크, 블로그 위치, 공유 방식, 진행 순서를 처음에 정해서 문서 구조가 흔들리지 않았다.
- **원본 폴더를 건드리지 않는 원칙.** upstream 업데이트를 merge하기 쉽고, 내 작업과 원본을 비교하기도 쉽다.
- **기존 자산을 재사용했다.** nu54v-dk의 보드 문서 덕분에 핀 제약(PWM은 P1 포트만, 빈 핀은 P2.00~P2.06 7개, VCOM0 문제)을 배선 전에 찾았다.
- **위험을 일찍 찾았다.** 모터 드라이버 칩 혼동(DRV8833은 3S 전압에서 손상), 엔코더 5 V 출력 문제를 부품 사진과 사양만으로 미리 걸렀다.
- **Issue 번호와 README 링크가 처음부터 맞았다.** Issue를 만들기 전에 링크를 #1~#8로 정해 두었다.

## 3. 시간이 걸린 점과 원인

| 문제 | 원인 | 다음에는 |
|---|---|---|
| README를 두 번 썼다 (원본 README 위에 한국어를 덧붙임 → 원본 내용을 지우고 새로 씀) | README의 독자와 범위를 먼저 묻지 않았다 | 공개 문서는 **독자·범위·톤**을 먼저 정하고 쓴다 |
| 하드웨어 표를 일반적인 부품으로 가정해서 썼다가 고쳤다 | "부품이 이미 있다"고만 받고 모델명은 받지 않았다 | 사양이 필요한 정보는 **모델명·판매 링크·사양 이미지**를 처음에 받는다 |
| Part 0 검증(Docker 빌드)을 끝내지 못했다 | Docker 데몬이 꺼져 있었고, 켜려면 sudo가 필요하다 | 세션 시작 때 **사전 조건을 점검**한다 (Docker, 보드 연결, NCS) |
| 기어비가 아직 추정값이다 | 판매 사양 이미지에 기어비가 없다 | 실측 항목은 Issue 체크리스트에 넣고, 하드웨어가 손에 있을 때 먼저 잰다 |
| 이미지 파일명 오타(`encorder`)로 옮기는 작업이 생겼다 | 올릴 위치와 이름 규칙이 없었다 | 이미지는 `docs/images/`에 영어 소문자 이름으로 올린다 (CLAUDE.md에 규칙 추가) |

## 4. 결과물에 빨리 도달하기 위한 개선

### 4-1. 하드웨어 작업을 앞당긴다 (가장 효과가 큼)

지금 순서는 Part 1 → 2 → 2.5 → 3으로 직렬이다. 그런데 Part 3의 하드웨어 브링업(배선, IMU 읽기, 모터 구동, 엔코더 카운트)은 강화학습 결과와 상관이 없다.
**Part 1~2(시뮬레이션 학습)와 하드웨어 브링업을 같은 주에 나란히** 진행하면, 학습이 끝났을 때 바로 실물에 올릴 수 있다.
게다가 Part 2.5 모델링에 필요한 기어비, 모터 속도, 질량 측정이 브링업 중에 같이 나온다.

```
지금:   [Part1]→[Part2]→[2.5 측정·모델]→[3 배선·펌웨어]→[3 배포]
제안:   [Part1]→[Part2]→[2.5 모델]→[3 배포]
        [배선]→[IMU·모터·엔코더 CLI]→[측정값] ─┘ (나란히)
```

→ 반영함: 하드웨어 브링업을 Issue [#9](https://github.com/AntonSangho/reinforcement-learning-for-robotics-nu54/issues/9)로 분리하고, Part 3(#5)은 추론·제어 루프·배포만 남겼다.

### 4-2. 세션 진행 방식

| 시점 | 할 일 |
|---|---|
| 시작 | `docs/00_progress.md` 읽기 → 이번 세션의 Issue 하나 고르기 → 사전 조건 점검 |
| 진행 | Issue 체크리스트 순서대로. 학습 질문은 **예측 → 실행 → 설명** 순서로 (값을 바꾸기 전에 결과를 먼저 예측해서 적는다) |
| 학습 실험 | 실험마다 하이퍼파라미터·결과·한 줄 해석을 기록 (`docs/experiments.md` 제안) |
| 끝 | Issue 체크 → README 진행표 → `00_progress.md` → 회고(짧게) → 메모리/CLAUDE.md 갱신 → 커밋·push |
